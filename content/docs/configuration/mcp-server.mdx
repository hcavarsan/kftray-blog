title: MCP Server Integration

kftray's Model Context Protocol (MCP) server lets compatible clients browse Kubernetes resources, manage port forwards and change saved configs.

## Enabling

<Steps>
<Step>
Open Settings in kftray.
</Step>
<Step>
Find the MCP Server section.
</Step>
<Step>
Turn it on and set the port. The default is `3000`.
</Step>
</Steps>

The server runs in the background as part of kftray. It stops when kftray closes and starts again on the next launch if you left it enabled.

| Setting | Default | Description |
|---------|---------|-------------|
| Enabled | `false` | Whether the MCP server starts with the app |
| Port | `3000` | Port the server listens on |

## Connecting a client

Point an MCP client at:

```
http://localhost:3000/mcp
```

Clients that read server definitions from a config file usually need an entry like this:

```json
{
  "mcpServers": {
    "kftray": {
      "url": "http://localhost:3000/mcp"
    }
  }
}
```

The file location depends on the client, so check its documentation.

To check that the server is running:

```bash
curl http://localhost:3000/health
```

The server listens on `127.0.0.1` only and uses these routes:

| Route | Purpose |
|-------|---------|
| `POST /mcp` | JSON-RPC requests from the client |
| `GET /mcp` | Server-sent events stream |
| `DELETE /mcp` | Ends a session |
| `GET /health` | Health check |

## What it can do

The server exposes 16 tools in three areas.

Clients can browse clusters, control port forwards and manage the same saved configs as the desktop and terminal apps. The [examples](#examples) show tool calls for each task.

<Callout type="info" title="Shared state">
The MCP server, desktop app and terminal app share one database, `configs.db` in the [configuration directory](/docs/configuration#storage-location) (`~/.kftray` by default). Each interface shows configs and forwards created through the others.
</Callout>

## Examples

<Tabs items={['Browsing', 'Forwarding', 'Managing configs']}>
<Tab value="Browsing">

<Accordions>
<Accordion title="What clusters do I have access to?">
The client calls `list_kube_contexts`. kftray reads the kubeconfig and returns the context names, for example `dev-cluster`, `staging-cluster` and `prod-cluster`.
</Accordion>

<Accordion title="What services are in the payments namespace?">
The client calls `list_services` with the context and namespace. kftray queries the Kubernetes API and returns the service names, for example `payments-api`, `payments-worker` and `payments-db`.
</Accordion>

<Accordion title="What ports does redis expose?">
The client calls `list_ports` with the context, namespace and service name. kftray returns each port with its name, number, target port and protocol. If it can't find the service, it checks container ports on pods, using the name as a label selector.
</Accordion>
</Accordions>

</Tab>
<Tab value="Forwarding">

<Accordions>
<Accordion title="Connect me to payments-api on port 8080">
The client calls `start_port_forward` with the context, namespace, service name and remote port. kftray creates a config, starts the forward and returns the local port it assigned (for example `localhost:54321`). If the request names a local port, kftray uses that one. If the forward fails to start, kftray deletes the config it created.
</Accordion>

<Accordion title="Start config 3">
The client calls `start_port_forward` with only the config ID. kftray looks up the saved config, starts the forward and returns the local and remote ports.
</Accordion>

<Accordion title="Forward to pods labeled app=auth">
The client calls `start_port_forward` with `workload_type` set to `pod` and `target` set to `app=auth`. kftray finds a matching pod and starts the forward.
</Accordion>

<Accordion title="What's running right now?">
The client calls `list_active_port_forwards`. kftray returns every active forward with its config ID, service, namespace, ports, protocol and alias.
</Accordion>

<Accordion title="Stop the payments forward">
The client calls `stop_port_forward` with the config ID. kftray stops the forward and confirms which service it stopped.
</Accordion>

<Accordion title="Stop everything">
The client calls `stop_all_port_forwards`. kftray stops every active forward and returns how many it stopped.
</Accordion>
</Accordions>

</Tab>
<Tab value="Managing configs">

<Accordions>
<Accordion title="Save a config for grafana but don't start it">
The client calls `create_config` with the context, namespace, service and ports. kftray saves the config and returns its ID. It starts no forward until the client asks for one.
</Accordion>

<Accordion title="Export all my configs">
The client calls `export_configs`. kftray returns all saved configs as a JSON string with the total count.
</Accordion>

<Accordion title="Import configs from JSON">
The client calls `import_configs` with a JSON string. kftray imports the configs, and they appear in the GUI and TUI right away.
</Accordion>

## Tool reference

### Cluster browsing

| Tool | Required args | Returns |
|------|--------------|---------|
| `list_kube_contexts` | | context names |
| `list_namespaces` | `context` | namespace names |
| `list_services` | `context`, `namespace` | service names |
| `list_pods` | `context`, `namespace` | pods with name, status and labels |
| `list_ports` | `context`, `namespace`, `service` | ports with name, number, target port and protocol |

Every tool accepts an optional `kubeconfig` parameter. `list_pods` also accepts `label_selector`.

### Port-forward control

| Tool | Required args | Returns |
|------|--------------|---------|
| `start_port_forward` | `config_id`, or `context` + `namespace` + `remote_port` for a new forward | local port, remote port, config ID |
| `stop_port_forward` | `config_id` | service name, namespace |
| `stop_all_port_forwards` | | count of stopped forwards |
| `list_active_port_forwards` | | list of active forwards with config ID, service, namespace, ports, protocol, alias |

Without `config_id`, a new forward also needs `service` for a service workload or `target` (a label selector) for a pod workload. It also accepts:

- `local_port` and `protocol` (`tcp` or `udp`).
- `workload_type` (`service`, `pod` or `proxy`).
- `kubeconfig` and `alias`.

### Configuration management

| Tool | Required args | Returns |
|------|--------------|---------|
| `list_configs` | | configs with ID, alias, service, namespace, ports, protocol. Takes an optional `filters` list |
| `get_config` | `config_id` | full config details |
| `create_config` | `context`, `namespace`, `remote_port`, plus `service`, `target` or `remote_address` for a service, pod or proxy workload | config ID |
| `update_config` | `config_id` | success status |
| `delete_config` | `config_id` | success status |
| `export_configs` | | all configs as JSON |
| `import_configs` | `configs_json` | success status |

`list_configs` takes `filters`, a list of conditions that must all match. Each condition is `field=value[,value...]`, or a bare `field` for "is set". The fields are `context`, `namespace`, `kubeconfig`, `workload_type`, `protocol` and `tag:<key>`. For example, `["tag:team=payments"]`, `["namespace=api,web"]` or `["tag:pinned"]`.

`create_config` and `update_config` take a `tags` object. Tag keys use lowercase letters, digits, `.`, `_`, `-` and `/`, and an empty string value makes a key-only tag. `update_config` replaces the whole tag map, and `{}` removes all tags. See [tags, filters and group by](/docs/configuration/tags-and-views).

## Security

<Callout type="warn" title="Local only by default">
The server binds to `127.0.0.1`, so only processes on the same machine can reach it.
</Callout>

The MCP server uses the same kubeconfig credentials as the rest of kftray. It doesn't store or send credentials separately.
