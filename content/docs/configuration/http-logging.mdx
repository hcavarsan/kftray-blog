HTTP logging records requests and responses from TCP port forwards and HTTP exposes. It is off by default. Turn it on for each config.

The [HTTP logs video](https://www.youtube.com/watch?v=73PyGbMnNSY) shows the desktop logs opened in an editor.

<Callout type="error" title="Sensitive data in logs">
HTTP logs capture request and response headers and bodies, including authentication tokens, API keys and personal data. Turn logging on only while you debug, sanitize what you share and delete the logs when you finish.
</Callout>

## Enabling HTTP logging

<Tabs items={['Desktop', 'Terminal']}>
<Tab value="Desktop">

<Steps>
<Step>
Open the actions menu (the menu icon at the end of the row) for the port forward.
</Step>
<Step>
Select `Enable HTTP Logs`. The same item reads `Disable HTTP Logs` once logging is on.
</Step>
<Step>
Optional: select `HTTP Logs Settings` to change the log options for that config.
</Step>
</Steps>

![TCP forward actions menu with HTTP logging controls](/img/docs/http-logging-menu.webp)

The menu shows these items only for TCP forwards. Once logging is on, `Open HTTP Logs File` opens the log in your external editor or the system app for log files. kftray tries `EDITOR`, then `VISUAL`, then the system opener.

</Tab>
<Tab value="Terminal">

Press `l` to toggle HTTP logging on the selected configuration, or set `"http_logs_enabled": true` in your JSON config.

Press `L` to configure logging. The dialog accepts a size limit of 1 to 100 MiB and retention of 1 to 365 days.
It also lets you turn automatic cleanup on or off.

</Tab>
</Tabs>

Logging toggles apply to established TCP forward connections without reconnecting. Turning logging on starts capturing subsequent HTTP traffic. Application connections already upgraded to WebSocket mode ignore logging toggles.

## HTTP expose logging

HTTP exposes use the same logging controls as port forwards. Both public and cluster-only HTTP exposes record requests and completed responses in paired log entries.

For an expose config, set `http_logs_enabled` to `true`:

```json
{
  "alias": "local-api",
  "context": "dev-cluster",
  "namespace": "development",
  "workload_type": "expose",
  "protocol": "tcp",
  "local_address": "127.0.0.1",
  "local_port": 3000,
  "exposure_type": "cluster",
  "exposure_protocol": "http",
  "http_logs_enabled": true
}
```

The expose tunnel checks logging settings every second, so toggles and rotation settings apply without restarting the tunnel. Its reverse WebSocket transport still supports HTTP logging. Upgraded application WebSocket streams do not produce HTTP payload logs.

Raw TCP exposes (`exposure_protocol: "tcp"`) do not produce HTTP logs, even though their row menu shows the logging controls.

## Config fields

| Field | Default | Description |
|-------|---------|-------------|
| `http_logs_enabled` | `false` | Turns logging on for the config |
| `http_logs_max_file_size` | 10 MiB | Rotation threshold in bytes. Import accepts 1 byte to 100 MiB |
| `http_logs_retention_days` | 7 | Retention for rotated files when automatic cleanup is on. Import accepts 1 to 365 days |
| `http_logs_auto_cleanup` | `true` | Removes expired rotated files when the logger starts and after rotation |

The logger rotates a nonempty file before an entry would push it past the size limit. It copies the file to a timestamped file and truncates the active file. A single oversized entry can exceed the limit because the logger keeps each entry intact.

This example sets a 20 MiB rotation threshold and 14-day retention with automatic cleanup:

```json
{
  "alias": "api-debug",
  "target": "app=backend,version=v2",
  "namespace": "staging",
  "local_port": 3000,
  "remote_port": 8080,
  "context": "my-k8s-cluster",
  "workload_type": "pod",
  "protocol": "tcp",
  "http_logs_enabled": true,
  "http_logs_max_file_size": 20971520,
  "http_logs_retention_days": 14,
  "http_logs_auto_cleanup": true
}
```

## Log file location

HTTP logs live in the `http_logs` folder inside the [configuration directory](/docs/configuration#storage-location). kftray looks for the directory in this order:

1. `KFTRAY_CONFIG`
2. `$XDG_CONFIG_HOME/kftray`
3. `~/.kftray`

Each port forward writes its own file, named `<config id>_<local port>.http`:

<Files>
<Folder name="~/.kftray/http_logs" defaultOpen>
<File name="3_8080.http" />
<File name="3_8080_20261106_003000.http" />
<File name="4_8001.http" />
<File name="5_8002.http" />
</Folder>
</Files>

Rotated files use `<config id>_<local port>_<YYYYMMDD>_<HHMMSS>.http`, with a UTC timestamp. A numeric suffix distinguishes rotations within the same second.

An HTTP expose uses its local service port in the filename. An expose on local port `3000` writes `<config id>_3000.http` in the same folder.

## Log format

The `.http` files are plain text. The `#` lines and `###` separators match the VS Code REST Client format. Each request and each response is its own entry.

```
# ----------------------------------------
# Trace ID: a1b2c3d4
# Request at: 2026-02-09T14:32:15.123+00:00
POST /api/users HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Content-Length: 87

{"email":"user@example.com","name":"Jane Doe","role":"admin"}

###

# ----------------------------------------
# Trace ID: a1b2c3d4
# Response at: 2026-02-09T14:32:15.168+00:00
# Took: 45 ms
HTTP/1.1 201 Created
Content-Type: application/json
Content-Length: 156

{"id":"usr_123","email":"user@example.com","name":"Jane Doe","role":"admin"}

###
```

| Part | Detail |
|------|--------|
| Trace ID | Links a request to its response |
| Request at, Response at | RFC 3339 timestamps |
| Took | Response time in milliseconds |
| Request line, headers and body | The request as it went through the forward |
| Status line, headers and body | The response as it came back |

kftray decodes response bodies sent with `Content-Encoding: gzip`, `br` or a stacked value such as `gzip, br`. It shows other encodings as received.
The preformatted-response path cuts decoded bodies at 10 MiB and adds a truncation marker. Other response-formatting paths do not share that limit.

## Viewing and replaying in kftui

Press `V` to open the HTTP logs viewer. It has two modes.

List mode is the default:

- It shows all requests with timestamps and status codes.
- `↑` `↓` move through requests and `PageUp` `PageDown` scroll by ten entries.
- `Enter` opens the detail view for a request.
- `a` turns automatic scrolling for new requests on or off.
- `Esc` closes the viewer.

Detail mode shows the full request and response, including headers and body:

- `↑` `↓` and `PageUp` `PageDown` scroll the details.
- `r` replays the selected request with a 30-second timeout.
- `c` or `C` copies the selected request as a `curl` command through OSC 52. Your terminal must support OSC 52 clipboard writes.
- `Esc` cancels an in-progress replay and goes back to list mode.

Replay uses `http://<local_address>:<local_port>` from the forward, with `127.0.0.1` as the default address. A request path that already contains a full HTTP URL keeps that URL. Copy as `curl` uses the same address rules.

Press `o` to open the log file in your external editor. Request replay exists in kftui only.

## Cleanup

When automatic cleanup is on, the logger removes expired rotated files for the same config ID and local port. It checks file modification times when the logger starts and after each rotation. Cleanup leaves the active file and other forwards' logs in place.

To remove logs manually, stop the forward first. For the default configuration directory:

```bash
rm ~/.kftray/http_logs/*.http
```

If you changed `KFTRAY_CONFIG` or `XDG_CONFIG_HOME`, use that directory's `http_logs` folder instead. The command deletes active and rotated logs for every forward in that folder.
