kftray sends local traffic through the Kubernetes API to your cluster. It stores port-forward configs so you can reuse them.

## The Forwarding Pipeline

Every port forward goes through four phases:

<Steps>
<Step>
Configure: choose a target service, ports and protocol in JSON or the desktop app. kftray stores the config in a local SQLite database.
</Step>
<Step>
Connect: kftray authenticates with the Kubernetes API using your `kubeconfig` credentials. It opens a port-forward stream to the target pod or service.
</Step>
<Step>
Forward: local traffic on your chosen port flows through the Kubernetes API to the cluster service. For UDP, an in-cluster proxy converts the protocol.
</Step>
<Step>
Reconnect: kftray checks connection health. When pods restart, nodes restart or the network drops, it reconnects with longer waits between attempts.
</Step>
</Steps>

## TCP Forwarding

For TCP services, kftray works like `kubectl port-forward` and adds automatic reconnection and management of many forwards at once:

![TCP traffic travels from the local app through kftray and the Kubernetes API server to the target pod. Responses follow the reverse path.](/diagrams/tcp-forwarding.png)

When the target pod restarts, kftray detects the drop and reconnects to the replacement pod.

## UDP Forwarding

Kubernetes doesn't support UDP port forwarding natively, so kftray uses a proxy:

![kftray carries UDP traffic over TCP to the kftray-server proxy. The proxy converts it back to UDP for the target service. Responses follow the reverse path.](/diagrams/udp-forwarding.png)

kftray deploys a `kftray-server` pod to convert traffic between UDP and TCP. This adds one network hop and lets you reach DNS, DHCP and UDP-based message queues.

See [Proxy Forwarding](/docs/configuration/proxy-forwarding) for deployment details and configuration.

## Shared State Model

The desktop and terminal interfaces share one SQLite database at `~/.kftray/kftray.db`. The [MCP server](/docs/configuration/mcp-server) also reads it when you turn it on:

- Configurations created in one interface appear instantly in the other.
- Both interfaces show runtime status, including which forwards are active.
- Each app manages its own active forwards. To stop a forward, use the app that started it.

## Core Components

| Component | Role |
|---|---|
| `kftray-portforward` | Core forwarding logic, Kubernetes API integration and reconnection |
| `kftray-tauri` | Desktop GUI (Tauri framework), system tray and HTTP log viewer |
| `kftui` | Terminal interface with keyboard-driven management |
| `kftray-mcp` | [MCP server](/docs/configuration/mcp-server) that exposes port-forwarding operations to external clients |
| `kftray-server` | In-cluster proxy for UDP forwarding and proxy workloads |
| `kftray-commons` | Shared config models, SQLite database access and utilities |
| `kftray-helper` | Operations that need elevated permissions, such as hosts file edits and low-port binding |
| `kftray-http-logs` | HTTP traffic interception and logging |

For more architecture detail, see [Architecture](/docs/resources/architecture).
